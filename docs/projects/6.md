# Project brief — Move to TypeScript, Next.js and SST

The mandate is [#6](https://github.com/yedeya/playground-3d/issues/6)'s body (`K-PROJ-15`). Two sibling projects draw this one's edges, and both build on it: [#7](https://github.com/yedeya/playground-3d/issues/7) ports the Python model generator to TypeScript and GLB, and [#8](https://github.com/yedeya/playground-3d/issues/8) adds the backend, auth and the offline PWA. Six decisions in §7 need a person before this merges; three are technical and I settled them.

## 1. The real problem

**There is one problem here, not three, and it is that "working exactly as it does today" is not written down anywhere a machine can check.** The mandate has three parts: a language change, a framework change and a first deploy. Each is routine on its own. What makes them risky is that the app's behaviour lives almost entirely in code that no test reads:

- **The tests cover the data and the pure text helpers, and nothing else.** The tests in `tests/` hold 7 cases (`git grep -cE "^ *it\(" -- tests`). They check the model data and `parts.js`'s helpers. The panel, the filter-change rule in `main.js`, the colour modes and the viewer's colouring and picking have no test at all (`git grep -lE "createPanel|createViewer|createStore" -- tests` prints nothing).
- **No test counts as evidence yet.** `docs/qa/stack.md` declares no `## Code areas`, so `kanon-spec-coverage` reports that no runner runs the tests, and there was no spec area until this brief seeded `APP` and `PLAT` (`kanon-spec-coverage`: 0 of 26 locked). Any criterion this project cited would come back "not-run" from `verify-acs`.
- **The UI is imperative DOM code with no teardown.** The panel builds its chips with `innerHTML` and reaches the page through global ids, and the viewer creates its WebGL renderer, a `ResizeObserver` and a `window` listener. Neither hands back a way to dispose of them (`git grep -nE "return \{ home \}|store.subscribe|addEventListener" -- src`). Under React's strict mode, which mounts every component twice in development, that means doubled chips and two renderers. That is the one real porting hazard, and `[PLAT-5]` names it.

**So the systemic fix is to lock today's behaviour first and port second.** Issue A makes the existing tests count. Issue B adds characterization tests for the panel, the filter rule and the viewer's state-to-appearance and tap rules (`[APP-8]` to `[APP-15]`), on the plain-JavaScript code as it stands. Only then do Issues C and D change the language and the framework, with every `APP` test as the oracle. The deploy (Issues E to I) is separate work, and only shares the sequencing.

**Reconciliation gap: the test runner is undeclared, and that gap is Issue A.** `kanon-spec-coverage` reports 0 `[confirmed]` clauses with no test, because this repository had no spec until now. But it also reports that nothing runs the tests, so no clause can be verified. That is the gap this project would otherwise inherit (`K-SPEC-5`).

**The deploy target was checked, not assumed.** `gh api repos/yedeya/playground-3d/actions/oidc/customization/sub` answers `use_default: true` and `use_immutable_subject: true`, with the prefix `repo:yedeya@46228687/playground-3d@1446091910`. So, per `docs/lanes.md` ("The subject each role trusts"), the staging role must trust exactly `repo:yedeya@46228687/playground-3d@1446091910:environment:staging`, and the production role `repo:yedeya@46228687/playground-3d@1446091910:environment:production` (`[PLAT-7]`). A role that trusts `repo:yedeya/playground-3d:…` refuses every deploy. The repository has no GitHub environments yet (`gh api repos/yedeya/playground-3d/environments --jq '.environments[].name'` prints nothing). The adoption record waives `deploy.reference-undeclared` until this project declares a reference deploy.

## 2. Scope

**This project is:**

- tests that lock today's behaviour (`APP`), and the code areas that let `verify-acs` run them;
- the app, its tests and its config in strict TypeScript, still on Vite, and then on Next.js (App Router) with Vite removed;
- `sst.config.ts` on SST v4, with one `sst.aws.Nextjs` site (OpenNext) and two stages, `staging` and `production`;
- the two AWS deploy roles' trust policies as files, the roles and the GitHub environments set up by the Owner, and Kanon's deploy lane with its build, deploy and smoke hooks;
- the reference-deploy declaration that lets this and every later project close (`K-PROJ-11`);
- a production URL, a human check of the deployed app on a phone, and a week of measured cost.

**It is not:**

- **The model generator.** `model/build_playground.py` and `model/tools/render3.swift` stay as they are, and so does `npm run model`. Porting the generator to TypeScript and moving to GLB is #7, which says it builds on this project. `[PLAT-1]` counts JavaScript files only, so it holds while the Python stays. `[APP-1]` to `[APP-3]` become #7's part-for-part baseline.
- **A database, auth, user data or offline support.** These are #8's. The OpenNext internals SST deploys (a revalidation queue and table) are not the app's database. `[PLAT-6]` forbids any resource of the app's own beyond the site.
- **Rewriting the panel or viewer in React.** They stay imperative modules, mounted from one client component (decision 7). A React rewrite would change behaviour that only Issue B's tests and Issue H's check guard.
- **A browser end-to-end suite.** Real WebGL, touch and pinch zoom are checked once by a person (Issue H, decision 5). Playwright can come back in as a follow-up if the viewer starts changing often.
- **Transport groups and tape labels** (#9), and **running the brief guard in CI** (#10).
- **Dependabot for npm, release-please's release type, and an escalation-paths file.** This repository has no Merger lane (`git grep -l "Merge (Merger)" -- .github/workflows` prints nothing), so a person merges every pull request, and an escalation-paths file would change nothing today. It becomes worth writing on the day the Merger is installed.

**Specific to this project's definition of done:**

- **Every clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **The reference environment is `staging`** (`K-PROJ-11`'s default), deployed by `deploy.yml`'s `staging / deploy` job (`[PLAT-11]`). `verify-acs` runs the `APP` and `PLAT` tests at the release deployed there.
- **Two items are a person's, and gate closure:** Issue F (the AWS roles and GitHub environments) and Issue H (the first production deploy and the phone check). Issue I is a measurement item, and closes when its number is posted (`K-PROJ-16`).
- **Routing.** The app's own work (B, C, D, H) is `enhancement` on Product Backlog. Test evidence, infrastructure and the deploy pipeline (A, E, F, G, I) are platform work, so they are `pipeline-improvement` on Development Automation, where the platform bucket wins a tie (`K-WORK-4`).

## 4. Cost

**Estimated at $0 to $2 a month for both stages together, before any domain. The estimate is inferred, not measured. Issue I measures it.** Per stage, at one person's traffic:

| Resource (per stage) | Basis | Estimate |
|---|---|---|
| CloudFront | always-free allowance of 1 TB and 10 million requests a month | $0 |
| Lambda: OpenNext's server, image and revalidation functions | always-free allowance of 1 million requests and 400,000 GB-seconds a month, shared across the account | $0 |
| S3 assets, and SST's state bucket (one per account) | a few MB | under $0.05 |
| OpenNext's revalidation table and queue | on demand, idle | $0 |
| CloudWatch Logs | $0.50 per GB ingested, a few MB | under $0.05 |

Two stages double the line items, not the total, because the free allowances are account-wide. If the account's other projects already use up those allowances, Lambda and CloudFront bill per request, and at this traffic that is still cents. A custom domain adds $0.50 a month for a Route 53 hosted zone, plus the domain's yearly price if it is new (decision 3). GitHub costs nothing: the repository is public, so Actions minutes and environments with required reviewers are free (`docs/qa/adoption.md`, `## Plan`). There is no scheduled smoke check, so no schedule wakes anything (`K-OBS-10`). These prices are from my knowledge of AWS's public pricing, not from a bill. That is why Issue I exists, and decision 1 asks the Owner to agree to the range before Issue G's first deploy spends anything (`K-OBS-9`).

## 5. Observability

**I propose adding no alarm, and paging on nothing.** Whether to page is the Owner's call, so it is decision 10, not mine. The signals this project creates, and what watches each:

- **A failed deploy or smoke check.** Kanon's deploy lane already files `Deploy to <environment> failed` and `Smoke check on <environment> failed` with `sev:high` for production (`docs/lanes.md`, "After each environment"). That is the signal, and it needs nothing added.
- **CloudFront 5xx rate and the server function's errors.** Not paged. The app is a static viewer for one household, nobody depends on it being up, and a page would cost an alarm for no one to answer. Issue G records this in `docs/observability.md`'s not-paged table. The trigger that changes the answer is #8's backend, the first thing with data that can be lost.
- **Real-user errors in the browser.** Not collected. That would mean a third-party script or an endpoint of our own, which is #8's territory.

## 7. Decisions

1. **Spend: two stages, `staging` and `production`, both always on, at an estimated $0 to $2 a month plus any domain. ⛔ OPEN — awaiting the Owner.** I recommend agreeing to the range. The alternative, production only, saves almost nothing, because the free allowances are account-wide, and it makes production the reference environment, where agents must not explore (`K-OBS-7`). #8 has already put $1 to $3 a month for its database in front of the Owner, so this sits beside it. Issue I measures the real number.
2. **Which AWS account and region. ⛔ OPEN — awaiting the Owner.** I recommend a member account of its own for playground-3d, if the Owner runs AWS Organizations, so that decision 4's broad permissions stop at this app. Otherwise use the account the Owner's other SST apps use. For the region, I recommend the one those apps use, so #8's Aurora sits beside them. The account id goes into `KANON_DEPLOY_TARGETS`, which anyone can read on a public repository (`docs/lanes.md`). Say whether it may also appear in `infra/aws/`.
3. **The production URL: CloudFront's own domain, or a custom domain. ⛔ OPEN — awaiting the Owner.** CloudFront's `*.cloudfront.net` address costs nothing and needs nothing. A subdomain of a domain the Owner already holds in Route 53 costs $0.50 a month for the zone, if there is not one already. I recommend the subdomain if one exists, and CloudFront's address otherwise. Name the hostname, and Issue E carries it.
4. **The deploy roles' permissions. ⛔ OPEN — awaiting the Owner.** SST creates IAM roles for its functions, so the deploy role needs to create and pass IAM roles, which is close to admin in practice. There are two options: (a) `AdministratorAccess`, bounded by the exact-subject trust in `[PLAT-7]` and, for production, by the required reviewer (decision 6); (b) a hand-written least-privilege policy, which usually takes several failed deploys to get right. I recommend (a) if decision 2 gives the app its own account, and (b) if it shares an account with other apps.
5. **How "exactly as today" is checked: characterization tests under jsdom (Issue B), plus one person's check on a phone (Issue H), and no browser end-to-end suite. ⛔ OPEN — awaiting the Maintainer.** This is a product-verification rule, so it is not mine to settle. The alternative is a Playwright suite with WebGL in headless Chromium, which is a new tool, a browser install in CI and more items. I recommend the tests plus the phone check: the viewer rarely changes, and touch is what Issue H checks and Playwright would only simulate.
6. **Production deploys wait for the Owner's approval. ⛔ OPEN — awaiting the Owner.** The production environment gets the Owner as its required reviewer, so a release goes to staging on its own and to production only when the Owner approves. This is free on a public repository. The alternative is the `no-reviewers` fallback, where the Maintainer dispatches production by hand (`docs/lanes.md`). I recommend the required reviewer.
7. **The viewer and the panel stay imperative modules, mounted from one client component, and are not rewritten in React. ✅ ANSWERED (Lead, technical): mounted, not rewritten.** The mandate asks for unchanged behaviour, and a rewrite of the panel would re-derive every behaviour Issue B locks. Mounting needs only a dispose for each (`[PLAT-5]`). Carried into Issue D.
8. **Gates gain `npm run typecheck`. ✅ ANSWERED (Lead, technical): `npm test`, `npm run typecheck`, `npm run build`.** `next build` type-checks too, but a separate gate fails sooner and names the file. Carried into Issue C.
9. **The model JSON stays bundled into the client, as on Vite, rather than fetched from `public/`. ✅ ANSWERED (Lead, technical): bundled.** It is today's behaviour, and #7 replaces the format with GLB anyway, which is the moment to decide how a model is loaded. Carried into Issue D.
10. **Observability: no alarm, no paging (§5). ⛔ OPEN — awaiting the Owner.** I recommend the skip, with the trigger recorded in Issue G's `docs/observability.md`: the first backend (#8). Paging is the Owner's call (`K-OBS-1`, `K-PROJ-18`).
