# Project brief — Backend for user data and offline PWA

The mandate is [#8](https://github.com/yedeya/playground-3d/issues/8)'s body (`K-PROJ-15`). It builds on [#6](https://github.com/yedeya/playground-3d/issues/6), the move to TypeScript, Next.js and SST (brief in PR #11, not merged), and it is the platform that [#9](https://github.com/yedeya/playground-3d/issues/9), transport groups and tape labels (brief in PR #13, not merged), stores its plan on. [#7](https://github.com/yedeya/playground-3d/issues/7) (brief in PR #14) moves the model to a fetched GLB, which the offline app has to cache. The acceptance criteria are the `SYNC` clauses in `docs/qa/specs/sync.md` and the `PWA` clauses in `docs/qa/specs/offline.md`, both seeded in this pull request. Six decisions in §7 need a person before this merges. One is the Owner's own answer from the mandate, and four are technical ones I settled.

## 1. The real problem

**The mandate names three things: a backend, sign-in and an offline app. It is one problem: the app has nowhere to keep anything, and it has to keep it where there is no network.** "Offline" and "backend" pull in opposite directions. Data that must last months belongs on a server, and an app used in a van without signal cannot wait for one. So the design is local-first. Each device holds a full copy of the owner's data and edits it at once. A server copy in Aurora is the one that lasts, and a small sync protocol keeps the two the same. Sign-in only guards that sync. Offline is then not a feature added at the end: it is how every read and write works from the first day.

What I found in the code, each with the command that re-derives it:

- **The app stores nothing, anywhere.** `git grep -nE "localStorage|indexedDB|sessionStorage|fetch\(" -- src` prints nothing. The mandate's "could only live in one device's `localStorage`" describes the alternative to this project, not a store that exists. So there is no user data to move: **no data migration** (§6).
- **There is no app shell to cache yet, and nothing of the PWA exists.** `git grep -nliE "serviceWorker|manifest" -- src index.html vite.config.js` prints nothing. This repository is still Vite and plain JavaScript (`git grep -nE "vite|vitest" -- package.json`). #6 replaces both with Next.js on SST, so every service-worker and route decision here is made against #6's app, which is why this project waits for #6 (decision 6).
- **The page loads its fonts from Google.** `git grep -n "fonts.g" -- index.html` shows two preconnects and the Barlow stylesheet. A service worker cannot reliably precache another origin's font CSS, so offline the app would fall back to system fonts. `[PWA-3]` requires same-origin fonts. #6's brief already allows `next/font`, which hosts them on the app's own origin.
- **The model is part of the app shell.** Today it is a bundled JSON import (`git grep -n "speeltoestel.json" -- src`). #7 turns it into `/models/speeltoestel.glb`, fetched at runtime. `[PWA-2]` says "the model data in whatever form the app loads it", so it holds whichever of #7 and this project lands first.
- **The data is tiny.** #9's plan is at most 161 memberships, about ten pieces and a few dozen labels (#9's brief, §4). That is why a whole-state pull (`[SYNC-10]`) and whole-record last-write-wins (`[SYNC-12]`) are enough, and why the cost is all in waking the database, not in storing anything.

**Two cost facts shape the design.** Both are inferred from AWS's documentation as I know it, not measured.

- **Aurora Serverless v2 now pauses at 0 ACU, and resuming takes about 15 seconds.** Local-first hides that wait, because the owner never waits on the server. That is why `[SYNC-13]` answers a resuming cluster with 503 rather than holding the request.
- **Every request that reaches the database can wake it.** So `[SYNC-7]` keeps every unauthenticated request away from the database, sign-in included, and `[SYNC-15]` never syncs on a timer alone. An open phone on a table would otherwise keep the cluster awake all day.

**Reconciliation gap: none in these areas. The one that blocks evidence is #6's Issue A.** `kanon-spec-coverage` on this branch reports `SYNC` with 18 clauses and `PWA` with 6, all 0 locked, 0 `[confirmed]` without a test. It also reports that `docs/qa/stack.md` declares no `## Code areas`, so no test counts as evidence yet. #6's brief makes declaring the code areas its Issue A, and this project waits for #6, so declaring them here too would duplicate it.

## 2. Scope

**This project is:**

- an Aurora PostgreSQL Serverless v2 cluster per stage, reached through the Data API, declared in #6's `sst.config.ts`, with migrations that the deploy hook applies;
- a Drizzle schema with the account and sync tables, the schema-change ritual and the data-isolation rules in `docs/qa/stack.md`, and, if decision 4 says so, `docs/qa/escalation-paths.md`;
- the owner's sign-in, as decision 1 records;
- a generic sync protocol: collections, pull, push, idempotent retries and tombstones. #9 adds its tables to it as collections;
- the device's copy: IndexedDB, an outbox, the sync loop, a sync status, and sign-out;
- the PWA: a manifest, icons, a service worker that precaches the app shell and the model, same-origin fonts, and a safe update;
- the Owner's setup and a check on two real phones, and a month of measured cost.

**It is not:**

- **The transport plan's tables, screens or rules.** These belong to #9: its pieces, memberships and labels become collections of this project's sync (`[SYNC-9]`) in #9's Issue C. Until #9 lands, sync carries no user-visible data. This project proves itself with a test-only collection and with the phone check in Issue H. #9's own phone check covers "the same plan on a second device" (decision 8).
- **The stack move or the deploy lane.** #6 owns Next.js, SST, the two stages, the OIDC roles and the hooks. This project adds a cluster to `sst.config.ts`, a migration step to the deploy hook, and a permission grant to the roles if #6 chose least privilege. It changes nothing else of #6's.
- **More than one user, sharing, or a public sign-up.** There is one owner. Every row carries an `account_id` anyway (`[SYNC-5]`), because #9's `[TRANS-18]` scopes rows by account, and a second account later is then a sign-in change, not a data migration.
- **Hiding the viewer behind sign-in.** The 3D viewer stays public, as #6 deploys it. Only user data needs a session (decision 1).
- **Background sync while the app is closed.** The Background Sync API does not exist in Safari on iOS (inferred, from its documentation). The app syncs while it is open (`[SYNC-15]`), and the sync status says what has not been saved yet (`[SYNC-16]`).
- **Live updates between two devices that are both open,** such as a push or a socket. A device sees the other's changes the next time it starts, comes online or becomes visible. Nobody asked for more, and polling would keep the database awake.
- **A data export or a restore runbook.** Durability rests on 35 days of point-in-time backups, deletion protection, and a full copy on every device. A restore is an AWS console action for the Owner. Exporting to a file can come back if the owner wants a paper or file copy for the van.

**Specific to this project's definition of done:**

- **Every clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **Three clauses defer to decisions of this brief:** `[SYNC-6]` (decision 1), `[SYNC-12]` (decision 2), and the texts in `[SYNC-8]`, `[SYNC-16]` and `[PWA-5]` (decision 3). An answer here changes what they require without a spec edit.
- **`[SYNC-18]` is a person's verdict,** recorded on Issue H, and so is the live half of `[PWA-2]`. Issue I is a measurement item, and closes when its number is posted (`K-PROJ-16`).
- **One of #6's clauses is reworded.** `[PLAT-6]` says the app has "no database". Issue C rewords it to admit the cluster in `[SYNC-1]`. Today `[PLAT-6]` exists only on PR #11's branch.
- **Routing.** The schema rules, the infrastructure and the deploy step (A, C, D, I) are platform work: `pipeline-improvement` on Development Automation, where the platform bucket wins a tie. Sign-in, sync, the device's copy, the PWA and the phone check (B, E, F, G, H) are the app's own work: `enhancement` on Product Backlog (`K-WORK-4`).

## 4. Cost

**Estimated at $1 to $3 a month for both stages together, inside what the mandate approved. The estimate is inferred, not measured, and Issue I measures it.** The prices are AWS's public list prices as I know them, at $0.12 to $0.15 per ACU-hour depending on the region (#6's decision 2 chooses the region). I did not use a bill or a pricing API.

| Line (both stages) | Basis | Estimate a month |
|---|---|---|
| Aurora compute, production | about 30 openings a month that sync, each waking the cluster for about 10 minutes at 0.5 ACU: 2.5 ACU-hours. In a moving month, about 150 openings: 12.5 ACU-hours | $0.30 to $1.90 |
| Aurora compute, staging | about 10 wakes, from each release's migrations and from testing | about $0.10 |
| Secrets Manager | the cluster's credentials secret, which the Data API needs: one per stage, at $0.40 each | $0.80 |
| Aurora storage, I/O and backups | an almost empty database. Backups are free up to the cluster's own size | under $0.10 |
| Data API, Lambda, CloudFront | hundreds of requests a month | $0 |
| VPC | no NAT gateway, no endpoint and no public IPv4 address (`[SYNC-1]`) | $0 |
| AWS Budgets alert | the first two budgets in an account are free | $0 |

**About $1.20 in an ordinary month, and up to about $2.90 in a moving month.** The SST secrets for sign-in do not add Secrets Manager charges, because SST keeps them in its own state (inferred from SST v3). Nothing here runs on a schedule, so there is no tick to price (`K-OBS-10`). The migrations wake each cluster once per release, which is the staging line, and once more on production when the Owner approves the release.

**The risk is a cluster that never pauses.** At the 1 ACU cap, a cluster kept awake all month costs about $90 to $110. That happens only if something keeps sending it requests. `[SYNC-7]` keeps unauthenticated traffic away from it, and `[SYNC-15]` never polls, so only the owner's own use can wake it. Decision 7 adds a budget alert at $5 a month so that a mistake shows within a day, not on the bill.

**The Owner agreed to this in the mandate** ("approved at about $1–3 a month"), so decision 5 asks only about the limits that set the worst case. #6's own $0 to $2 sits beside this figure and is not part of it.

## 5. Observability

**I propose no paging and one cost alert. Paging is the Owner's call, so it is decision 7.** #6's brief named this project's backend as the trigger for reconsidering its no-paging answer, because this is the first data that can be lost. So I reconsidered it, signal by signal:

- **A sync that fails.** Not paged. The owner sees it in the app as unsaved changes (`[SYNC-16]`), and the change is kept until it is saved (`[SYNC-15]`). The person a page would reach is the person holding the phone. The trigger that changes this answer is a second user.
- **A migration that fails on deploy.** Already watched. It fails the deploy job (`[SYNC-4]`), and Kanon's deploy lane files `Deploy to <environment> failed` (`docs/lanes.md`, "After each environment"). Nothing needs adding.
- **The database losing data.** Not a signal anyone can alarm on usefully. What protects the data is deletion protection, 35 days of point-in-time backups (`[SYNC-1]`) and a copy on every device (`[SYNC-14]`).
- **Cost running away.** One AWS Budgets alert: an email to the Owner when the month's actual or forecast cost for `project = playground-3d` passes $5. It is free, and it is the only signal here that nobody would otherwise see until the bill. It needs #6's `project` cost-allocation tag to be active (#6's Issue F).

Issue C adds the first two as rows of `docs/observability.md`'s not-paged table, if #6 has created it by then.

## 7. Decisions

1. **How the owner signs in. ⛔ OPEN — awaiting the Owner.** This is an auth decision, so it is the Owner's. (a) One passphrase, stored only as a salted hash in a stage secret, and a signed session cookie valid for 400 days, on each device it is entered on (`[SYNC-6]`). No new service, about a hundred lines, and nothing in the database. Rotating the session key signs every device out. (b) Passkeys (WebAuthn): nothing to type and phishing-resistant, but a registration flow, credentials stored in the database, and a recovery path if the only registered device is lost. (c) Cognito or a Google login: a new service and redirect flows, for one person. I recommend (a). There is no rate limit on sign-in: a five-word random passphrase (about 64 bits) makes guessing hopeless without one, and a limit would need state the database must not be woken for. Also agree that the viewer stays public and only user data needs a session (§2). Carried into `[SYNC-6]`, `[SYNC-7]` and Issue E.
2. **When two devices change the same record, which change wins. ⛔ OPEN — awaiting the Maintainer.** This is what the user sees, so it is not mine (`K-PROJ-18`). (a) The change that reaches the server last wins, for the whole record. (b) The change made last wins, by the device's clock, which phones do not keep reliably. (c) The app shows the conflict and asks. I recommend (a). One owner rarely edits one record on two devices at once, and #9's records are small: a membership is one part's piece, so there is nothing inside a record to merge. Carried into `[SYNC-12]` and Issue F.
