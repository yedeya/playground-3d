# Project brief — Port the model generator to TypeScript and GLB

The mandate is [#7](https://github.com/yedeya/playground-3d/issues/7)'s body (`K-PROJ-15`). It builds on [#6](https://github.com/yedeya/playground-3d/issues/6), the move to TypeScript, Next.js and SST, whose brief is PR #11 and not merged. Two siblings touch the same model: [#9](https://github.com/yedeya/playground-3d/issues/9) (transport groups and tape labels, brief in PR #13) keys its stored plan on the part ids this project must keep, and [#8](https://github.com/yedeya/playground-3d/issues/8) (backend and offline PWA, no brief yet) will have to cache the GLB this project introduces. The acceptance criteria are the `MODEL` clauses in `docs/qa/specs/model.md`, seeded in this pull request, plus four of #6's `APP` clauses that the switch to GLB rewords. Four decisions in §7 need a person before this merges; four are technical, and I settled them.

## 1. The real problem

**The mandate reads as one port, but it is two changes with different risks, and the plan keeps them apart.** Translating the generator from Python to TypeScript is mechanical, and its risk is silent drift: a part that moves a few millimetres, or a module that loses a plank, with every test still green. Changing the model format from JSON to GLB is not mechanical: it moves the part metadata the app depends on into a binary file, and it turns a bundled import into a fetch the app has to wait for. So the systemic fix is to lock today's model as a readable baseline first, port the generator against it (Issue A), and only then change the file (Issue B), what the app loads (Issue C), and what gets deleted (Issue D).

What I found in the code, each with the command that re-derives it:

- **The generator is one self-contained Python file with no input.** It uses the standard library only (`git grep -n "^import\|^from" -- model/build_playground.py`), takes nothing but an output directory, and builds every part from constants, so its output is a pure function of the file. Its triangulation is its own ear-clipping routine (`git grep -n "def triangulate" -- model`), which the port has to carry over too, because the baseline compares triangles.
- **It writes four files, and only one reaches the app.** Two USDA scenes, a CSV and the web JSON (`git grep -nE "write_(usda|csv|web)\(os" -- model`). The JSON is copied to `src/data/speeltoestel.json` by `npm run model` (`git grep -n '"model"' -- package.json`). The USDA files feed the Mac Quick Look recipe and the Swift render tool in `docs/HANDOVER.md` (`git grep -nE "usdzip|render3" -- docs/HANDOVER.md`). Nothing in the repository reads the CSV (`git grep -l "parts.csv" -- ':!docs/projects'` lists only the generator and the handover). "One model format, GLB" therefore deletes three outputs and one tool, which decision 1 puts to the Maintainer.
- **Today's model is 161 parts in 11 modules, 22 of them estimates.** `grep -o '"id":"[A-Z0-9]*_[A-Za-z0-9_]*"' src/data/speeltoestel.json | wc -l` prints 161; `grep -o '"module":"[A-Z0-9]*"' src/data/speeltoestel.json | sort -u | wc -l` prints 11; `grep -o '"source":"estimate"' src/data/speeltoestel.json | wc -l` prints 22.
- **The check against the manual is two assertions.** The stock counts per code, 25 codes from `P-220` to `handle`, and unique ids (`git grep -nE "^STOCK|def check|assert " -- model`). The port keeps both, as functions a test can feed a broken part list (`[MODEL-3]`, `[MODEL-4]`).
- **The swap switch has only ever run one way.** `SWAP_LADDER_SLIDE` mirrors the ladder's parts and the slide about x = 1095 mm and reverses their winding (`git grep -n "SWAP_LADDER_SLIDE" -- model`). It is on, and the only test checks the on position. `[MODEL-5]` makes both positions buildable in one process and tests the off one, which #9's decision about the real playset may need. The mirror reverses each polygon face's vertex order before triangulation (`git grep -n "LEN - v\[0\]" -- model`), and the ear clipping starts at the face's first vertex, so it cuts each mirrored quad along its other diagonal. The off position's triangles are therefore not the on position's triangles mirrored. `[MODEL-5]` checks the property both positions share: triangle counts, mirrored vertex positions, and outward-facing triangles.
- **The Dutch name is not in the model data at all.** The app derives it from `module` and `group` with `kindOf` (`git grep -n "kindOf" -- src`). The app reads `id`, `module`, `kit`, `group`, `size`, `source`, `natural` and `tri` from each part, plus `moduleColors` (`git grep -nE "part\.(id|module|kit|group|size|source|natural|tri)|moduleColors" -- src`). So "the Dutch name must survive in the GLB" means the generator starts writing it, and decision 7 keeps `kindOf` its one source.
- **The viewer's look depends on the geometry being unindexed.** It builds each part from a flat triangle list and calls `computeVertexNormals`, which on unindexed triangles gives one normal per face, and it draws edges at a 25° threshold (`git grep -nE "computeVertexNormals|EdgesGeometry" -- src`). An indexed GLB, the usual output of glTF tools, would smooth the shading across every plank's corners. `[MODEL-7]` and `[MODEL-10]` keep it unindexed.
- **The model is bundled, and the panel is built before the viewer from it.** `git grep -n "speeltoestel.json" -- src tests` shows the import in the app and the test. A fetched GLB gives the panel a loading state it has never had, and a new failure that the existing `#fail` text contradicts, since that text says the parts list still works (`git grep -n 'id="fail"' -- index.html`). `[MODEL-11]` and decision 2 cover both.
- **Size.** The JSON is 168,951 bytes (`wc -c src/data/speeltoestel.json`) and holds about 34,000 coordinates (`grep -o ',' src/data/speeltoestel.json | wc -l` prints 33,991, which also counts the metadata's commas). As float32 positions that is roughly 136 KB, so the GLB will be about the JSON's size. That is inferred, not measured, and it is why compression is out of scope.

**Why the baseline has a 1 mm tolerance.** There are two causes, and the second is certain. First, the geometry uses `sqrt`, `cos`, `sin`, `acos` and `atan`. Python's maths library and V8 may differ in the last bit of those, and the JSON rounds every coordinate to whole millimetres, so a coordinate near a half millimetre can round the other way. That is inferred, not observed: my shell runs neither runtime. Second, Python's `round()` rounds an exact half to the even neighbour, and JavaScript's `Math.round` rounds it up. So any coordinate that is exactly x.5 mm comes out 1 mm apart unless the port copies Python's rounding. Either cause moves a coordinate by at most 1 mm, so the tolerance is inclusive. Metadata, part order and triangle counts must match exactly, and each coordinate must be at most 1 mm from the baseline's (`[MODEL-2]`, decision 5).

**Reconciliation gap: none in this area, and the one that blocks evidence is #6's Issue A.** On `main` there is no spec. `kanon-spec-coverage` on this branch reports `MODEL` with 13 clauses, 0 locked and 0 `[confirmed]` without a test, and it reports that `docs/qa/stack.md` declares no `## Code areas`, so no test counts as evidence yet. #6's brief makes declaring them its Issue A. This project waits for #6 (decision 3), so doing it here too would be a duplicate. If decision 3 is answered "start now", Issue A below gains that declaration. (`kanon-spec-coverage` crashes without `docs/qa/specs/_locked-floor.json`, which is #12; this branch adds the same empty floor the sibling briefs add.)

## 2. Scope

**This project is:**

- the generator in TypeScript under `model/`, building the same 161 parts, with the stock check, the id check and the swap switch;
- a readable baseline of today's model in `tests/fixtures/`, which the generator must match part for part, and which changes only on purpose;
- the GLB: one node per part with its metadata and Dutch name, written by `npm run model` and committed;
- the app loading the GLB instead of the JSON, with a loading state and a load failure of its own;
- removing the Python generator, its USDA and CSV outputs and the Swift render tool, and the README and handover text about them, in Dutch;
- a smoke check that the deployed app can fetch its GLB (decision 4).

**It is not:**

- **A change to the model's geometry.** The port is faithful by construction (`[MODEL-2]`). The uncertainties `docs/HANDOVER.md` lists (the 22 estimates, the bridge sag, the canvas heights) stay as they are, and so does the swap. #9's Issue B may turn the swap off. If it merges after this project's Issue C, it refreshes the baseline with `npm run model -- --baseline` in its own pull request. Before then, that option does not exist or does not reach the app, and §6 says what it must do instead.
- **The stack move.** TypeScript configuration, the typecheck gate, Next.js, `public/` and the deploy hooks are #6's. This project uses them and changes none, except the smoke hook (Issue E). #6's `[PLAT-1]` (no JavaScript tracked) holds throughout, because the generator is TypeScript.
- **New part data.** Transport groups and labels are #9's, keyed by part id. The GLB carries today's fields and the Dutch name only.
- **Offline caching of the GLB.** #8's PWA will have to precache `/models/speeltoestel.glb`; that belongs in #8's brief, and I note it there rather than build it here.
- **Mesh compression (Draco, meshopt).** At about the JSON's size it would add a decoder to the client to save little. It comes back if the model grows past a megabyte.
- **The module names.** `MODULES` and `MODULE_ORDER` stay in the app's domain module; the GLB carries module colours because the JSON did.
- **A person's check of the result.** Not needed: `[MODEL-2]`, `[MODEL-7]` and `[MODEL-10]` make the geometry's identity a machine check, and #6's Issue H already puts a person on the deployed app.

**Specific to this project's definition of done:**

- **Every clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **Issue C rewords #6's `[APP-1]` to `[APP-3]`** in `docs/qa/specs/app.md`, because they describe the JSON (`tri` lists divisible by 9). That file exists only on PR #11's branch today, which is one reason this project waits for #6.
- **The project cannot close before #6 deploys.** `docs/qa/adoption.md` waives the reference deploy until #6 declares one, and `verify-acs` runs at the reference environment (`K-PROJ-11`).
- **Routing.** Issues A to D are the app's own work, `enhancement` on Product Backlog. Issue E changes a deploy hook, so it is `pipeline-improvement` on Development Automation (`K-WORK-4`).

## 4. Cost — no delta

**No delta: $0 a month.** Nothing new runs. The GLB is a static file of about the JSON's size, deployed in the same artifact as the app's scripts by #6's pipeline, and served from the same CDN within the free allowance #6's §4 prices. The repository is public, so CI minutes are free (`docs/qa/adoption.md`, `## Plan`). Committing a binary of roughly 150 KB each time the geometry changes grows the history slowly; the model JSON has been committed once and never changed since (`git log --oneline -- src/data/speeltoestel.json`). Issue E adds one HTTP request per smoke check, which costs nothing. No schedule wakes anything (`K-OBS-10`).

## 6. Blast radius — what will need a human

**The scope-first bail list:**

- **Data migration: none.** There is no stored data. #9's future plan refers to parts by id, and `[MODEL-2]` keeps every id.
- **Auth, credential or security change: none.** Nothing here touches the deploy roles, OIDC or secrets.
- **Destructive schema: none.** There is no database.

**Softer items:**

- **Pipeline files.** Issue E edits `.github/actions/smoke`, and Issue A may edit `docs/qa/stack.md`. Each escalates under `K-MERGE-4`, and with no Merger lane a person merges every pull request here anyway.
- **Deleting a tool the user has used.** Issue D removes the Quick Look recipe and the Swift renderer, which the handover documents for the user's Mac. That is decision 1, settled here rather than in Issue D's review.
- **A cross-project ordering hazard.** Issue C edits `docs/qa/specs/app.md`, which only #6's brief creates, and needs #6's Next.js app and `public/`. Decision 3 makes the wait explicit, because the dependency graph cannot name another project's issues. #9's Issue B (PR #13) is a second hazard. If decision 2 there is (b), it turns the swap off and regenerates the model, which changes the geometry `[MODEL-2]`'s baseline records. Its own §6 says the two projects must not run at once and the Owner sequences them. Here, the two safe windows are:
  - **before this project's Issue A starts**, so Issue A copies a baseline that already has the swap off and ports the switch in its new position;
  - **after this project's Issue C merges**, when `npm run model` runs the TypeScript generator, `--baseline` exists, and the app loads the GLB. #9's Issue B then sets the TypeScript switch and runs `npm run model -- --baseline`.

  Anywhere between those two points, the change can be lost with every test green. Until Issue B merges, `npm run model` still runs the Python (`git grep -n '"model"' -- package.json`), and `--baseline` does not exist. If #9's Issue B sets the swap flag off "in the current generator" and regenerates the JSON, the TypeScript generator keeps the swap on and still matches the old fixture, so `[MODEL-2]` stays green. This project's Issue B then writes the GLB from the TypeScript generator, `[MODEL-8]` compares the GLB only with that generator, and Issue C makes the app load it. At that point the ladder and slide are swapped again, which is the geometry #9's labels are placed on.

  So while this project's Issue A is open, #9's Issue B does not merge, because the baseline copy and the port are in flight on another branch. If it has to merge after Issue A merges and before Issue C merges, its pull request does all three of these:
  - it sets the switch the same way in both generators, Python and TypeScript;
  - it regenerates the JSON from the Python. After this project's Issue B, `npm run model` no longer copies the JSON, so it runs the Python and copies its web JSON by hand;
  - it refreshes `tests/fixtures/model-baseline.json` from that JSON by hand. After this project's Issue B, `npm run model -- --baseline` does the same from the TypeScript generator and also rewrites the GLB, which `[MODEL-8]` requires.

  I traced this hazard from the two briefs' text and ran nothing. I am raising it for the Owner's decision 3 and do not settle it.
- **Spec bookkeeping.** This branch, PR #11 and PR #13 each add `docs/qa/specs/_id-registry.json`, so whichever merges second has a one-line conflict to resolve by keeping every prefix. The allocator already numbered `MODEL` above the other branches' claims.

## 7. Decisions

1. **"One model format" retires the USDA scenes, the CSV, the Swift render tool and the Quick Look recipe. ✅ ANSWERED (Maintainer, 2026-11-05): retire all four.** The mandate asks for one format and one language, which implies all four, but it names none of them, and the handover documents the Quick Look and render steps as the user's way to look at the model on a Mac. I recommend retiring all four. The app itself is the viewer now; a GLB opens in Blender and in browser glTF viewers, and Apple's Reality Converter turns a GLB into a USDZ for Quick Look, which Issue D's handover text would mention (that conversion is from my knowledge, not tried). The alternative, a second USDZ output, contradicts the mandate. Carried into Issue D and `[MODEL-12]`.
2. **What the page shows while the GLB loads, and when it cannot. ✅ ANSWERED (Maintainer, 2026-11-05): the Lead's states, with the texts in English: `Loading model…`, and on failure `The model can't load. Reload the page or try another browser.` Transcribed into `[MODEL-11]` on this branch.** Today neither state exists. I recommend: the stats line reads `Model laden…` and the panel stays empty until the model is in; on failure the `#fail` element reads `Het model kan niet laden. Laad de pagina opnieuw of probeer een andere browser.`, because its present text promises a working parts list that a missing model cannot give. Those texts are `[MODEL-11]` as seeded; a different answer is transcribed into that clause on this branch before the merge.
3. **Nothing is dispatched until #6's Issue D, the move to Next.js, has merged. ✅ ANSWERED (Owner, 2026-11-05): `lead:file-only` comes off #7 only after #6's Issue D merges.** #7 carries `lead:file-only`, so the merge files these issues and dispatches none until the Owner removes the label. I recommend removing it only after #6's Issue D merges. By then the TypeScript setup, `public/` and `docs/qa/specs/app.md` exist, and #6's Issue A has made tests count as evidence. The alternative is to remove it after #6's Issue C (TypeScript on Vite), which lets Issues A and B run in parallel with #6's framework move. But the dispatcher would then send Issue C as soon as B closes, possibly before Next.js exists, and Issue C would be written twice. Either answer must also sequence #9's Issue B, if it runs, into one of the two safe windows §6 names: before this project's Issue A starts, or after its Issue C merges. If #9's Issue B lands after Issue A merges and before Issue C merges, it must follow §6's procedure: set both generators' switch, regenerate the JSON, and refresh the baseline fixture by hand. It does not merge while Issue A is open.
4. **Issue E extends the smoke check to the GLB. ✅ ANSWERED (Owner, 2026-11-05): yes. Since #6's decision 1 the only environment is `production`, so the check runs there.** It makes a missing model on staging or production file `Smoke check on <environment> failed`, where today nothing would notice (§5). I recommend it: it costs nothing and catches the one failure this project adds that no test can. If the answer is no, the Lead deletes Issue E and `[MODEL-13]` from this branch before the merge.
5. **The part-for-part match is checked against a readable baseline, with a 1 mm tolerance on coordinates. ✅ ANSWERED (Lead, technical): `tests/fixtures/model-baseline.json`, exact metadata, order and counts, coordinates at most 1 mm from the baseline's.** A binary GLB cannot be reviewed in a diff; the baseline can, and it survives the Python's removal, so `verify-acs` can still run `[MODEL-2]` when the project closes. The tolerance is §1's rounding argument. A deliberate geometry change refreshes the baseline with `npm run model -- --baseline` and shows up as a reviewable diff. Carried into `[MODEL-1]`, `[MODEL-2]` and Issue A.
6. **The GLB is committed and checked for drift, not built during `npm run build`. ✅ ANSWERED (Lead, technical): committed at `public/models/speeltoestel.glb`, with `[MODEL-8]` failing `npm test` when it is stale.** It is how the JSON works today, it keeps the generator out of the app's build and deploy, and a fixed path is what Issue E's smoke check fetches. Carried into Issue B.
7. **The Dutch name in the GLB comes from the app's `kindOf`, and the app reads it back from the GLB. ✅ ANSWERED (Lead, technical): one function, imported by the generator.** A copied naming table in the generator would drift from the one `[APP-6]` tests. The visible text stays the same. Carried into `[MODEL-6]`, `[MODEL-9]` and Issues B and C.
8. **The GLB writer and the TypeScript runner are the Implementer's choice, inside two limits. ✅ ANSWERED (Lead, technical): any writer added as a dev dependency only (`@gltf-transform/core` or a small hand-written one), and the client loads with three's `GLTFLoader`, adding no runtime dependency.** For running the generator, Node 24's built-in type stripping avoids a dependency; `tsx` is the fallback if the app's TypeScript settings get in the way. Either writer must produce identical bytes on every run (`[MODEL-8]`). Carried into Issue B.
